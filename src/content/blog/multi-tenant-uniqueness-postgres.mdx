DeployLog is a hosted changelog for developers, a Next.js app on Supabase with one Postgres database shared by every customer. The plan item read: before inserting a new project, check its slug against all existing projects and suggest a free one. Standard defensive move. The reviewer, an adversarial plan-review agent with no context on the feature, did not object to the idea. It objected to the premise.

Not hard. Not racy. Impossible.

## Why the app cannot look

Every table in DeployLog has row-level security enabled: sixteen tables, sixteen enable statements, and an event trigger that switches it on for any table created later. The create-project route runs on the session client, the Supabase client built from the user's cookies, and RLS filters every query it makes down to rows the caller's organization owns.

So "select all projects with this slug" doesn't fail on that client. It does something worse: it succeeds and returns only your own org's rows. Another tenant's `my-app` project is invisible to the query by design. The pre-insert check would come back clean, the insert would violate the constraint anyway, and the code would read like it handled a case it cannot see.

![One projects table for every tenant. A dashed bubble surrounds Org A, the caller, with docs and api. Org B, outside the bubble and invisible under row-level security, holds my-app. A select for my-app returns zero rows and reads clean; the insert of my-app fails with 23505 on projects_slug_key, raised by the row the query could not see.](/images/blog/multi-tenant-uniqueness-postgres/rls-bubble.svg)

The classic argument against check-then-insert is the race window between the two statements. RLS is stronger than that: there is no window because there is no check. The database's isolation guarantee, the entire point of RLS, is exactly what makes the app-level invariant unenforceable.

![Three panels. Check then insert with one tenant leaves a race window between the two statements. Check then insert under RLS has no window at all, because the check answered for one tenant and the insert fails with 23505. The constraint alone is one insert statement that returns 201 or 23505, atomic, with no read and no privilege escalation.](/images/blog/multi-tenant-uniqueness-postgres/check-then-insert.svg)

## The constraint is the only enforcement

Slugs in DeployLog need to be globally unique, not per-org, because public changelog URLs resolve slugs across all tenants. That invariant lives where an invariant across tenants has to live, in the schema:

```sql
ALTER TABLE projects ADD CONSTRAINT projects_slug_key UNIQUE (slug);
```

The migration that added it also had to backfill: existing cross-org collisions got suffixed `-2`, `-3` by creation order before the constraint could apply. Retrofitting an invariant means paying for the time it didn't exist.

With the constraint in place, the app's job inverts. Instead of preventing the conflict, it responds to one. Postgres reports a unique violation as error code 23505, and inside the create route's insert loop it is the one error that does not end the request:

```ts
if (!error) {
  return NextResponse.json({ data: project }, { status: 201 })
}
// 23505 = unique violation (this org's per-org slug, or another org's global
// slug). Any other error is not a collision, so fail fast.
if (error.code !== '23505') {
  return NextResponse.json(
    { error: { code: 'SERVER_ERROR', message: 'Failed to create project' } },
    { status: 500 },
  )
}
```

The route slugifies the name, attempts the insert, and on 23505 retries with `base-2` up to `base-10`, ten attempts in all. Only when every candidate collides does the user see a 409 asking for a different name. Nobody should see it; the suffixing absorbs collisions silently.

![The ladder of insert attempts. Attempt 1, my-app, 23505. Attempt 2, my-app-2, 23505. Attempt 3, my-app-3, 201 created, the usual exit. Attempts run to my-app-10, and only if all ten collide does the route answer 409 with: Could not generate a unique URL for this project name. Try a different name. MAX_SLUG_ATTEMPTS is 10 in src/lib/slug.ts.](/images/blog/multi-tenant-uniqueness-postgres/retry-ladder.svg)

One nuance in the error message: the route cannot say "taken by another organization," because it cannot know that, and confirming another tenant's slug would itself be a small information leak. The generic message is the only honest sentence available.

## The wider lesson

The transferable rule: in an RLS-scoped app, any app-level check of a cross-tenant invariant is theater. Your query runs inside one tenant's bubble, so it validates against a fraction of the data and returns confident nonsense. Uniqueness, quotas across tenants, global reservations, all the same shape. Declare the invariant in the schema, let the database throw, and translate the error at the boundary.

![Uniqueness, quotas and reservations share one shape, a fact about every tenant's rows. An app-level check on the session client answers for one tenant. The rule in three steps: declare it in the schema, let the database throw 23505, translate at the boundary into a 409 with a generic message.](/images/blog/multi-tenant-uniqueness-postgres/invariant-rule.svg)

There is a service-role client that bypasses RLS, and the temptation is to use it for the check. Don't. Widening a user-facing route's privileges to make an unnecessary query is backwards; the constraint already enforces the invariant atomically, with no privilege escalation.

How this was caught matters more than the fix. No test ran, because there was no code yet. The plan went through an adversarial review by an agent with no context on the feature and one job, poke holes. "The client you'd run this check on cannot see the rows" is precisely the kind of structural fact a plan's author glides past, because the plan reads correct from the inside.
