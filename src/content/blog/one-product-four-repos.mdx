DeployLog is a hosted changelog: you push an entry when you deploy, and it shows up on a public page, in a feed, and in a widget on your own site. Each of those delivery surfaces has a different consumer and a different deploy pipeline, which is why each ended up in its own repo.

Four repos for a solo project sounds like overhead. The split earns its keep. But it also created a class of bug I had to learn to respect.

## The satellites, briefly

The widget is the piece I'm most careful with, because it runs on other people's sites. It is vanilla TypeScript compiled by esbuild to a single self-contained script (an IIFE), about 4 KB gzipped, rendering into a closed Shadow DOM so the host page's CSS and mine can't touch each other. Integration is one script tag with data attributes for project, position, and theme. No framework, because a changelog bubble has no business shipping one to someone else's page.

The CLI (`npm i -g deploylog`, which installs the short alias `dpl`) posts entries from the terminal: `dpl push -t "v1.2 shipped" --from-git --ai-summarize`. `--from-git` builds the body from the commits since the last tag; `--ai-summarize` sends that text to the API, which rewrites it into release notes for end users with Claude Haiku. The Action does the same from CI, turning a GitHub release into a changelog entry. Two inputs are required, `api-key` and `project`. Four of the optional ones run the same Haiku rewrite (`ai-summarize`), publish at once instead of saving a draft (`notify-subscribers`), skip release candidates (`skip-prerelease`), and set the entry type (`entry-type`).

Both talk to the same API, authenticated with keys that start with `dk_`. The app itself is the dashboard, the public changelog pages, and that API.

## The tax: merged is not deployed

With one repo on Vercel, merge means live. With satellites, every repo has its own definition of shipped: the widget ships when Cloudflare Pages builds it, the CLI ships when a version hits npm, the Action ships when a release is tagged and the Marketplace picks it up.

This bit me. I merged a widget fix and moved on, but the CDN kept serving the old bundle, because the widget's `dist/` is gitignored and Cloudflare Pages had no build command set. It was publishing the repo as-is, which meant a stale artifact. The fix was two fields in the Pages settings, a build command and an output directory. The rule I took from it: for every satellite, know exactly which event produces the deployed artifact, and verify at the consumer's end after shipping.

![Three steps and a fix. A git push changes src/widget.ts, but dist/ is gitignored so the repo holds no bundle. Cloudflare Pages, with an empty build command, publishes the repo as-is and produces no dist/. The CDN keeps serving the previous widget.js: merged, not deployed. The fix is two fields in the Pages settings, build command npm run build and output directory dist.](/images/blog/one-product-four-repos/stale-artifact.svg)

## Edge caching makes it subtler

The widget's data endpoint runs on the edge and serves with `s-maxage=300, stale-while-revalidate=60`. Five-minute cache, and the right call: every page view on every site that embeds the widget hits this endpoint, and a changelog does not change every five minutes. The RSS and JSON feeds carry the same header.

But it means one product now has two clocks. Publish an entry and the server-rendered changelog page shows it instantly, while embedded widgets and feed readers keep getting the pre-publish payload for up to five minutes. Nothing is broken. The surfaces just disagree for a window.

![Two clocks. The origin box is the server-rendered changelog page, cache-control private and no-store, fresh on the next request. The edge box is the widget data, the RSS feed and the JSON feed, with s-maxage 300 and stale-while-revalidate 60, answered from the edge copy. A timeline from publish: for 300 seconds the edge may still serve the old payload, for the next 60 it serves the stale copy while it refetches, and after that it is fresh.](/images/blog/one-product-four-repos/two-clocks.svg)

I hit this while recording demo footage: published an entry, pointed the capture at a widget, and got the old notification state. Now the rule is to verify freshness at the exact surface I'm about to look at, `curl` the cached endpoint and check the `x-vercel-cache` and `age` headers, not the origin. Vercel strips the `s-maxage` on the way out, so the response only says `cache-control: public`; those two headers are the ones that tell you whether you are looking at the edge copy and how old it is. A cache-busting query string does not help, because it is a different cache key and the original stays stale. Once the window has passed, the next plain fetch is what triggers the refresh, so the check doubles as the fix.

![Terminal output of the same curl against the live widget data endpoint for the demo project, filtered to the cache headers and run twice. Past the five minute window the response reads cache-control public, age 301 and x-vercel-cache STALE. Run again after the refresh it reads age 30 and x-vercel-cache HIT.](/images/blog/one-product-four-repos/curl-headers.svg)

## Would I split again?

Yes, with one caveat. The split is about blast radius and cadence: the widget must stay tiny and boring, the CLI versions independently, the Action's releases follow Marketplace conventions, and none of them should redeploy because I restyled the dashboard.

The caveat is discipline. Four repos means four deploy pipelines to hold in your head, and a mental model where "it's merged" is where shipping starts. Write down how each satellite deploys the day you create it. You will need the note sooner than you think.
